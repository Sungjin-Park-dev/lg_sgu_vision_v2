# 현장 시운전 (2박 3일)

시뮬레이션에서 맞춰둔 셀 기하·카메라·충돌 모델을 실제 로봇에서 확인한다.
**측정 → 반영 → 무동작 검증 → 저속 동작 → 전체 실행** 순으로, 로봇을 움직이지 않고
잡을 수 있는 오류를 먼저 전부 잡는다.

먼저 [로봇에서 실행하기](execute-on-robot.md)의 안전 확인과
[Isaac 실행 모드](../guides/isaac-modes.md)의 모드 조합을 읽는다.

> ⚠️ **가장 큰 리스크는 셀 기하 불일치다.**
> 씬 YAML 의 **테이블 위치는 아직 추론값**이다 — 시작 자세에서 팔이 향하는 방향으로 역산한
> `+91.7612°` 회전. 물체 배치만 아루코로 실측했다. 테이블이 틀리면 계획은 성공하는데
> 실물이 긁힌다. **Day 1 을 건너뛰고 움직이지 않는다.**

---

## 가기 전 — 여기서 끝내둘 것

### PRE-1 `headless_mode` 인자 추가

지금 launch 가 드라이버에 `headless_mode` 를 안 넘긴다. UR 드라이버 기본값이 `false` 라,
이대로면 펜던트에서 **External Control 프로그램을 수동으로 재생**해야 드라이버가 붙는다.
현장에서 헤맬 지점이라 미리 넣는다.

### PRE-2 Isaac Inspection 앱 한 바퀴

최근 추가·변경한 UI 를 **아직 한 번도 눌러보지 않았다**: `Log Joints`, `Set Pose`(프레임
토글·접기), 그리고 world 원점 이동 뒤의 Generate / Preview / Execute.
**현장에서 처음 누르지 않는다.**

### PRE-3 URSim 으로 리허설

Day 2~3 의 명령 흐름을 하드웨어 없이 한 번 밟아둔다.

```bash
# 호스트
docker start ursim                     # 고정 IP 192.168.56.101
# 전원 + 브레이크 (또는 http://192.168.56.101:6080 펜던트에서)
exec 3<>/dev/tcp/192.168.56.101/29999
printf 'power on\n'      >&3 ; sleep 6
printf 'brake release\n' >&3 ; sleep 4
exec 3<&- ; exec 3>&-

# ros-jazzy 컨테이너
ros2 launch scripts/moveit/ur20_real_moveit.launch.py \
    use_mock_hardware:=false robot_ip:=192.168.56.101
```

URSim 이 **검증하지 못하는 것**: 셀 기하 일치, 실제 관성·처짐, 안전정지 배선, 네트워크 지연,
카메라 실물 정렬. 그래서 현장이 필요하다.

**가져갈 것**: 줄자, 아루코 마커(테이블용·받침대용), 카메라 각도 비교용 사진

## Day 1 — 측정과 셀 확정 (로봇 무동작)

### P0 도착 점검 · 무동작

1. 전원만 투입. **브레이크 해제하지 않는다.**
2. 펜던트에서 **현재 관절값**을 읽어 기록 → `ROBOT_START_STATE` 와 대조
3. 비상정지 위치·동선 확인, 로봇 반경 안 정리
4. 카메라가 플랜지에 물린 방향을 **사진**으로 남긴다 (clocking `-90°` 확인용)

**통과** — 비상정지에 손이 닿고, 관절값이 기록됨

### P1 실측 — 줄자 2회, 아루코 2회 · 무동작

1. 줄자: **바닥 → 마운트 기둥 상면** (기대 `805 mm`)
2. 줄자: **바닥 → 테이블 상면** (기대 `630 mm`)
3. 아루코: **테이블 마커** — 이게 셀 회전 추론을 실측으로 바꾼다
4. 아루코: **받침대 마커** — 물체 배치 재확인 (이미 1회 측정됨)
5. 마커를 **평평하게** 붙인다. 이전 측정은 `11.08°` 기울어 나왔다

**통과** — 줄자 값이 805 / 630 과 ±10 mm 이내. 아루코 `rx, ry` 가 0 에 가까움

**불일치 시** — 줄자가 다르면 **줄자를 믿는다**(`MOUNT_HEIGHT`, 테이블 `dimensions` 수정).
아루코만 다르면 카메라↔TCP 캘리브레이션의 원점 기준을 의심한다(우리 기준은 flange + 141 mm).

### P2 config 반영 + 재검증 · 무동작

1. 아루코 값을 **base_link 로 변환**해 씬 YAML 에 반영 (아래 [변환식](#아루코--씬-yaml-변환))
2. 테이블 위치를 실측으로 교체 → 추론값 `+91.7612°` 는 폐기
3. `check_ik.py` 재실행 → 도달률 확인
4. Isaac 을 띄워 **눈으로** — 테이블·받침대·물체가 실제 셀과 같은 배치인가

```bash
uv run --no-sync scripts/core/trajectory/check_ik.py \
    --object sample \
    --viewpoints data/sample/viewpoint/74/viewpoints_delaunay+agglomerative.h5 \
    --output /tmp/ik.h5
```

**통과** — 도달률이 기준선(`72/74`)에서 크게 안 떨어짐

**떨어지면** — 물체를 옮길지, viewpoint 를 다시 생성할지 판단.
**Day 1 안에 정리한다** — Day 2 동작이 여기 의존한다.

### P3 무동작 미러링 · 무동작 — 가장 가성비 높은 검증

드라이버만 붙이고 Isaac 이 실제 로봇을 미러링하게 한다. **로봇은 여전히 명령으로 안 움직인다** —
손으로 프리드라이브해서 화면과 실물을 나란히 본다.

```bash
# 셸1 — Isaac (real 모드), 뜨면 ▶ Play
source /workspace/.venv/bin/activate
OMNI_KIT_ACCEPT_EULA=YES python scripts/apps/isaac_pipeline.py \
    --object sample --mode real --pipeline-mode inspection

# 셸2 — 드라이버 + MoveIt
ros2 launch scripts/moveit/ur20_real_moveit.launch.py \
    use_mock_hardware:=false robot_ip:=<실기 IP>
```

1. `/joint_states` 가 펜던트 값과 일치하는가
2. 화면 로봇이 실물과 **같은 자세**인가 — 프리드라이브로 흔들어 확인
3. `Log Joints` 눌러 값 확인
4. RViz 에 카메라와 장애물 7개가 보이는가

**통과** — 실물을 움직였을 때 화면이 같이 움직이고, 자세가 눈으로 일치

**다르면 중단** — 화면과 실물 자세가 다르면 **Day 2 로 넘어가지 않는다.**
프레임·캘리브레이션 문제를 먼저 찾는다.

## Day 2 — 동작 검증 (저속)

### P4 MoveIt 조그 + 충돌 차단 확인 · 저속

1. 현재 자세에서 **몇 cm 만** 이동. 손은 비상정지에
2. **막혀야 할 것이 막히는지** — 테이블 아래를 목표로 주면 계획이 거부되어야 한다
3. 카메라 충돌 확인 — 카메라만 닿는 자세로 시도

```
# 카메라만 테이블에 닿는 자세 (계획이 거부되어야 함)
[83.8, 46.2, 87.4, -74.1, -46.4, -84.5] deg
```

**통과** — 막혀야 할 목표가 거부되고, 허용 목표는 정상 계획됨

**통과되면 중단** — 막혀야 할 것이 통과되면 **즉시 정지.** 충돌 모델이 안 들어간 것이다.

### P5 Plan/Move to Start — 계획된 접근 · 저속

Inspection 패널의 `Plan to Start` 가 **현재 자세에서** 충돌-free 경로를 계획해 고스트로
자동 재생한다. 경로를 눈으로 확인한 뒤(다시 보려면 `Preview in Simulation` 의 `Play`)
`Move to Start` 로 실행한다. 임의 이동보다 안전하므로 첫 자동 이동으로 쓴다.

**통과** — 계획이 나오고, 실행 경로가 Preview 와 같음

**경로 없음** — `plan exit code = 2` 면 계획이 남지 않아 `Move to Start` 가 회색 그대로다.
물체를 옮기거나 자세를 바꿔 재시도.

**거부** — 계획 후 로봇이 움직였으면 `Move` 가 실행을 거부하고 재계획을 요구한다.
`Plan to Start` 를 다시 누른다.

### P6 검사 궤적 1개 저속 완주 · 저속

1. Preview 로 전 구간 확인
2. `Execute Scan` — **속도를 낮춰서**
3. 완주 후 `Plan to HOME` → 확인 → `Move to HOME`

**통과** — 드롭 없이 완주, 계획 시간과 실제 시간이 비슷(속도 스케일링 개입 없음)

### P7 카메라 이미지 검증 · 저속

지금까지 검증되지 않은 축이다. viewpoint 는 **WD 172.23 mm, FOV 50×50 mm** 가정으로 만들어졌다.
WD 는 **카메라 끝(렌즈 배럴 앞면)에서** 잰다 — 자로 직접 확인할 수 있다. 벤더 공칭 250 mm 는
카메라 몸체 앞면 기준이라 같은 물체면을 가리키는 다른 숫자다(차 77.770 mm).

- 검사면이 화면을 채우는가 — FOV 가정 확인
- 초점이 맞는가 — WD 확인. **자를 대는 곳은 렌즈 배럴 앞면**이다
- 이미지 회전이 예상과 같은가 — clocking `-90°` 확인

**틀리면** — WD/FOV 는 **viewpoint h5 에 박제**돼 있다. config 만 고치면 기존 h5 는 안 바뀐다 —
재생성이 필요하다([카메라 기하 표준](../reference/camera-geometry.md)).

## Day 3 — 전체 실행과 회수 (정상 속도)

### P8 나머지 물체 배치 실측 · 전체

지금 `sample` 만 아루코 실측값이다. `curved_structure`, `cylinder_sample`,
`square_structure` 는 **스윕 추정값**이고 z 도 서로 다르다(`0.19` / `0.359`).
같은 받침대를 쓴다면 전부 같은 위치여야 한다.

- 물체별로 실제 놓는 자리를 확인 — 같은 받침대인가
- 배치가 바뀌면 `check_ik` → 필요시 GLNS 재생성

### P9 전체 궤적 완주 · 전체

1. 물체별 전체 검사 궤적을 정상 속도로
2. 사이클 타임 기록 — 계획값과 대조
3. 반복 재현성 확인 (같은 궤적 2~3회)

### P10 부가 기능과 경계 조건 · 전체

- Tilt 궤적 (부채꼴 검사)
- Pipeline mode 전환 — Inspection ↔ MoveIt 컨트롤러 활성화가 매끄러운가
- `Cancel` 이 계획 단계·실행 단계 모두에서 듣는가

### P11 회수 — 리포에 남길 것 · 무동작

- 실측 셀 기하 (줄자 + 아루코 **원본값**, 변환 전후 모두)
- 확정된 `ROBOT_START_STATE` / HOME 자세
- 물체별 배치 실측값
- 카메라 실측 WD/FOV, 샘플 이미지
- 사이클 타임 실측
- **안 된 것과 그 이유** — 다음 방문 계획의 입력

## 현장 참조

### 아루코 → 씬 YAML 변환

아루코/RTDE 는 **UR 컨트롤러의 `base` 프레임**으로 값을 준다. 우리 설정은 전부
**`base_link`**(ROS REP-103)다. 둘은 **Z 축 180°** 차이라 원점도 Z 축도 같지만 X/Y 가
반대다 — 그대로 넣으면 물체가 정확히 반대편에 놓인다.

```
x_base_link = -x_aruco
y_base_link = -y_aruco
z_base_link =  z_aruco          # z 는 그대로

회전: R_base_link = Rz(180°) · R_aruco
      → 회전벡터 성분의 부호를 뒤집는 것으로는 안 된다
```

Isaac 앱의 `Set Pose` 에서 **Input frame = `base (UR pendant/ArUco)`** 를 고르면 6개 값을
그대로 붙여넣을 수 있다. `flat` 체크는 마커 기울기를 버린다.
배경: [로봇·카메라 에셋 정의 지도](../reference/robot-camera-assets.md).

### 확정된 기준값

| 항목 | 값 | 근거 |
|---|---|---|
| 바닥 → 로봇 베이스 판 | 805 mm | 실측 확인 |
| 바닥 → 테이블 상면 | 630 mm | 실측 확인 |
| 테이블 상면 (base_link) | −175 mm | 위 둘에서 유도 |
| flange → 카메라 광축 원점 | 218.770 mm | CAD 실측 (렌즈 배럴 앞면 = 카메라 끝) |
| 카메라 clocking | roll −90° | 실기 대조 |
| 작업거리 (WD, 카메라 끝 기준) | 172.23 mm | 벤더 공칭 250(몸체 앞면 기준) − 77.770 · **현장 미검증** |
| FOV | 50 × 50 mm | 가정값 · **현장 미검증** |
| sample 배치 (base_link) | −1.1228, −0.2489, 0.0018 | 아루코 실측 |
| 도달률 기준선 | 72 / 74 | 위 배치에서 |

### 중단 기준

- 화면의 로봇 자세가 실물과 다르다 → **움직이지 않는다**
- 막혀야 할 목표가 계획을 통과한다 → **즉시 정지**, 충돌 모델 확인
- 계획 시간과 실제 실행 시간이 크게 다르다 → 속도 스케일링이 개입 중, 원인 확인
- 테이블·받침대 위치가 화면과 눈에 띄게 다르다 → **Day 1 으로 돌아간다**

## 아직 열려 있는 질문

| 질문 | 왜 중요한가 |
|---|---|
| 카메라↔TCP 캘리브레이션의 **카메라 원점**이 어디인가 | 우리 기준은 flange + 141 mm(몸체 앞면). 다르면 아루코 값이 광축 방향으로 계통 오차를 갖는다 |
| 이전 마커 측정의 **11.08° 기울기** | 평평한 면에 붙였다면 안 나와야 할 값. 자세 추정 계통 오차의 신호일 수 있다 |
| 물체 4종이 **같은 받침대**를 쓰는가 | 씬의 z 가 서로 다르다(0.19 / 0.359). 스윕이 높이를 자유롭게 고른 결과라 실제와 다를 수 있다 |
| MoveIt planning group tip 은 `tool0` 인데 xrdf `tool_frames` 는 `camera_optical_frame` | 원리적으로 정합하지 않는다. 현재 계획은 되지만 cuMotion 에서 걸리면 여기를 본다 |

---

기준 프레임은 전부 `base_link`. 아루코/펜던트만 `base` 이고, 입력 경계에서 한 번 변환한다.
이 문서의 수치는 **시뮬레이션 기준**이며, 현장 실측으로 대체되는 것이 목적이다 —
바뀐 값은 P11 에서 리포에 반영한다.
